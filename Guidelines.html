새 스레드 시작 절차

  1. Guidelines.html을 먼저 읽고, 현재 작업이 큐 상태를 바꾸면 해당 카드를 갱신한다.
  2. README.md와 HANDOFF.md에서 GitHub Pages 배포 방식, 로컬 preview 방식, 프로젝트 방향을 확인한다.?현재 저장소 안에는 별도 AGENTS.md 파일이 없으므로 대화에서 제공된 AGENTS 지침을 함께 적용합니다.
  3. 프로젝트 기준은 현재 저장소의 Guidelines.html, Design.html, README.md, HANDOFF.md 내용을 우선한다.
  4. git status --short --branch로 선행 변경과 현재 브랜치를 확인한다.?다른 스레드나 사용자가 먼저 만든 변경을 덮지 않기 위한 최소 확인입니다.
  5. 현재 대기 큐에 맡을 작업이 있으면 해당 카드를 ACTIVE_QUEUE_START 아래로 옮기고 상태와 배지를 진행 중으로 바꾼다.
  6. 미래 대기 태스크가 바로 실행 가능해지면 FUTURE_WAIT_QUEUE_START에서 WAIT_QUEUE_START 아래로 승격한다.
  7. 작업 범위, 수정 예정 파일, 검증 계획을 카드에 적고 시작한다.
  8. 개별 구현 작업은 담당 카드 코드 기반 git worktree와 codex/<task-code> 브랜치를 기본값으로 둔다.
  9. 작업자 검증이 끝나면 카드를 VERIFY_QUEUE_START 아래로 옮기고, 다음 항목에 사용자 QA 또는 통합 담당 확인 지점을 명시한다.
  10. 구현 카드는 사용자 QA 또는 통합 담당 확인이 기록되기 전까지 DONE_QUEUE_START 아래로 옮기지 않는다.
  11. 파일 수정 전, 주요 구현 후, 검증 후, 최종 응답 전에 담당 카드를 갱신한다.

공통 작업 원칙

  • 피드백과 문서는 한글로 작성한다.
  • Design.html은 최종 결정된 구현 기준과 그 결정 사유를 정리하는 문서다. 중간 산출물, 대화 히스토리, 임시 비교 과정은 최종안이나 다음 버전이 나오면 제거하고, 필요한 경우 이미지·영상·소리처럼 바로 이해되는 자료를 본문 설명보다 우선한다.
  • 기획서 작성 중 생긴 후보 이미지·영상·소리, 비교표, 접촉시트, 임시 변환물, 폐기 초안은 프로젝트 루트 $Trash 아래에만 둔다. DesignAssets/GuidelinesAssets에는 현재 최종 문서가 실제 참조하는 확정 자료만 둔다.
  • 새 게임 기획서의 첫 얼개는 핵심 방향, 세계와 공간, 레벨과 콘텐츠 구조, 캐릭터와 성장, 규칙과 계산 모델, 아이템과 경제, 퀘스트와 이벤트, 상호작용과 전투, 연출과 커뮤니케이션, UI와 편의 시스템, 메타 시스템, 미결정/제외 기준을 기본 후보로 삼는다. 장르에 맞지 않는 범주는 최종 문서에서 삭제하거나 합친다.
  • 마지막 기획 결과물 이후 코드가 직접 수정되어 Design.html과 다르면, 코드가 구현 기준이다. 기획서는 사용자의 말과 결정 사유를 나중에 검증하기 위한 정리 문서이므로 코드와 최신 의도에 맞춰 갱신한다.
  • 시스템 규칙 설명이 아닌 기획 방향, 아트, 감각 섹션은 이미지, 카드, 짧은 판단 기준을 먼저 보여주고 긴 문단은 접힘 영역이나 세부 설명으로 내린다.
  • 현재 기획 기준에서 탈락했거나 사용하지 않는 내용은 비교용 기록으로 쌓지 않고 삭제한다. 필요한 결정 이유만 현재 기준 가까이에 짧게 남긴다.
  • 이미지 생성 프롬프트처럼 작업자에게만 필요한 문구는 Design.html 본문에 노출하지 않고, 필요하면 Guidelines.html의 접힌 작업자용 참고에 둔다.
  • 롤백이 어려운 작업, 예를 들어 push, 완전 삭제, 되돌리기 어려운 문서 변경은 직전 대화에 명시 지시가 없으면 허가를 받는다.
  • 새 텍스트 파일은 UTF-8 No-BOM과 CRLF를 기본으로 한다. 기존 파일은 원본 인코딩과 줄바꿈을 유지한다.
  • 다른 스레드나 사용자가 만든 unrelated 변경은 되돌리지 않는다.
  • 사용자가 직접 손댄 코드나 미커밋 변경은 기본적으로 현재 의도가 담긴 작업물로 본다. 명시 요청 없이 되돌리거나, 스타일 정리·리팩터링 명목으로 덮어쓰거나, 기존 구현을 새 판단으로 갈아치우지 않는다. 같은 파일을 고쳐야 하면 요청 범위에 필요한 최소 hunk만 수정하고 기존 사용자 변경과 공존시킨다.
  • MunpaWeb은 정적 브라우저 게임이다. 사용자가 명시적으로 선택하기 전까지 서버, 백엔드, 패키지 매니저, 빌드 시스템을 추가하지 않는다.
  • 서비스워커나 오프라인 캐시는 직접 파일 열기만으로 판단하지 않고 localhost, 127.0.0.1, HTTPS에서 확인한다.
  • Guidelines.html은 무시 대상이 아니다. 작업 상태나 공유 규칙이 바뀌면 이 보드도 함께 갱신한다.

검증과 커밋 원칙

  • Design.html, Guidelines.html, DesignAssets, GuidelinesAssets는 opt-in 커밋 대상이다. 사용자가 문서 커밋을 명시하거나 해당 파일을 직접 지목하거나 문서 변경 포함을 지시한 경우에만 스테이징한다.
  • 코드나 게임 에셋 작업 뒤의 단순한 “커밋해”는 문서 파일 포함 지시가 아니다. 문서 변경이 남아 있으면 스테이징하지 말고 최종 보고에 미커밋 문서 변경으로 따로 언급한다.
  • 일반 문서 변경은 git diff --check, UTF-8 No-BOM, CRLF, 큐 마커 보존을 확인한다.
  • JS 변경은 번들 Node를 우선 사용한다: C:\Users\oojjr\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe --check src\app.js.
  • 서비스워커 관련 변경은 src/app.js의 APP_VERSION과 sw.js의 CACHE_NAME을 함께 확인한다.
  • 같은 워킹트리에서 커밋할 때는 git add -A를 습관적으로 쓰지 않고, 자기 변경 파일만 명시적으로 스테이징한다.
  • 커밋 직전에는 git diff --cached --name-status로 스테이징된 파일이 자기 범위인지 확인한다. 이 목록에 문서 파일이나 문서 자산이 보이면 명시 지시가 있었는지 다시 확인한다.
  • push는 로컬 커밋과 다르게 되돌리기 어려우므로 직전 대화에 명시 지시가 없으면 진행하지 않는다.

제품 방향

  • 정체성: MunpaWeb은 GitHub Pages로 공개되는 서버리스 브라우저 게임이다.
  • 배포: main 푸시 시 GitHub Actions의 Deploy GitHub Pages workflow가 정적 파일을 _site로 복사해 배포한다.
  • 저장: 큰 저장 데이터는 브라우저 저장소와 앱 런타임 흐름에 맞춰 유지하고, 작은 선호값과 최근 저장 메타데이터는 localStorage를 사용한다.
  • 오프라인: 서비스워커와 Cache Storage로 앱 셸 캐시를 관리한다.
  • 기술 방향: 브라우저 네이티브 기술을 우선하고, 패키지/빌드 시스템은 요구가 명확해질 때만 도입한다.
정적 사이트 유지 서버나 백엔드 없이 GitHub Pages에서 플레이 가능해야 한다.
브라우저 SPA 흐름 화면과 모달은 history.pushState, replaceState, popstate 복원 계약을 유지한다.
캐시 버전 동기화 앱 셸 캐시 변경 시 APP_VERSION과 CACHE_NAME을 함께 맞춘다.

예상 주요 작업

  • 게임 화면 흐름: 시작, 캐릭터/문파 생성, 플레이 화면, 기록/엔딩 화면의 브라우저 history 복원 안정화.
  • 저장 데이터: munpaweb:save:local, munpaweb:records:local, munpaweb:welcomeSaveStartedAt 키와 호환되는 저장/복원 관리.
  • 서비스워커: 앱 셸 목록, 네트워크 우선 fetch, 자동 활성화와 1회 reload 정책 점검.
  • 초상화 자산: 런타임 기본 캐릭터는 assets/style-exploration/characters/character-style-k/n-*.png, 제자 초상화는 assets/portraits/disciples/를 쓰며 src/app.js와 sw.js 캐시 목록을 함께 동기화.
  • UI 품질: 한국어 줄바꿈, 모바일 하단 조작, 고정형 선택 그리드, 명확한 인터랙션 상태 유지.

구현 기준

  • GitHub Pages에서 직접 동작해야 하므로 상대 경로, 정적 자산 경로, 서비스워커 scope를 신중히 본다.
  • 로컬 quick check는 index.html 직접 열기로 가능하지만, 서비스워커 검증은 .\serve.ps1 또는 serve.bat의 http://127.0.0.1:4173/에서 한다.
  • 사용자가 명시하지 않은 대형 리팩터링, 배포 workflow 변경, 공개 URL 변경은 하지 않는다.
  • PowerShell 출력의 한글 깨짐은 파일 손상으로 단정하지 말고 rg 또는 명시적 UTF-8 읽기로 다시 확인한다.
  • Guidelines.html은 작업용 운영판이므로 현재 workflow 복사 목록에 포함하지 않는다.

큐 갱신 규칙

카드 소유권?병렬 스레드가 서로의 진행 상황을 덮어쓰지 않게 하는 최소 규칙입니다. 한 스레드는 자기 카드만 수정한다. 다른 스레드 카드 정리는 사용자가 명시적으로 요청했을 때만 한다.
상태 이동?대기, 진행 중, 검증, 완료 중 하나로만 두어 전체 보드 상태를 빠르게 읽게 합니다. 실행 가능한 일은 현재 대기 큐에 둔다. 시작하면 진행 중으로 옮기고, 작업자 검증이 끝나면 검증으로 옮긴다. 사용자 QA 또는 통합 담당 확인이 기록된 뒤에만 완료 기록으로 옮긴다.
기록 밀도 한 항목은 짧게 쓴다. 범위, 현재 상태, 다음 행동, 수정 파일, 검증 결과, 막힌 사유가 보이면 충분하다.

스레드 상태 큐?동시에 돌아가는 Codex 스레드가 지금 무엇을 하는지 보는 운영 보드입니다.

브라우저에서 이 파일을 열어 전체 스레드 상태를 봅니다. 검색어를 입력하면 카드가 즉시 필터링되고, 카드를 누르면 상세가 펼쳐집니다.
